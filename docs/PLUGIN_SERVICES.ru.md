# Услуги плагинов (JSON-RPC)

[English](PLUGIN_SERVICES.md) | **Русский**

> **Роль документа:** контракт *услуг* – именованных возможностей, которые плагин предоставляет ядру и другим плагинам; вызовы идут сообщениями JSON-RPC 2.0.
> **Контекст:** [PLUGIN_BOUNDARIES.ru.md](PLUGIN_BOUNDARIES.ru.md) (что остаётся в ядре), [PLUGIN_DEVELOPMENT.ru.md](PLUGIN_DEVELOPMENT.ru.md) (как писать плагин), [ARCHITECTURE.ru.md](ARCHITECTURE.ru.md) §6.
> **Статус:** контракт описан; функции Host API из §6 ещё не экспортированы (запланированы в следующей версии ABI).

---

## 1. Назначение и роли

**Услуга** – именованная возможность с версией, например `search.files`. **Поставщик** – плагин, который регистрирует услугу. **Вызывающий** – ядро или другой плагин, который посылает услуге запрос.

Слой услуг – единственный способ поручить плагину задачу без новой функции Host API на каждую задачу. Первая услуга – `search.files`: через неё Alt+F7 использует быстрый индекс файлов (плагин Everything) или быстрый поиск по содержимому (плагин ripgrep) вместо собственного обхода диска. Тот же механизм позже обслуживает другие задачи (метаданные, предпросмотр) и мост к внешним процессам.

Чем услуга не является: она не заменяет контракты VFS, панели и диалога. Строки панели по-прежнему поставляет VFS-схема; услуга отвечает на вопрос и возвращает данные.

## 2. Модель услуги

| Термин | Смысл |
|---|---|
| Имя | Слова в нижнем регистре через точку: `search.files`. У одного поставщика имена уникальны; несколько поставщиков могут зарегистрировать одно имя |
| Версия | Положительное целое. Поставщик повышает её, когда меняется смысл поля; новые необязательные поля версию не меняют |
| Приоритет | Целое; поставщики одного имени перебираются по возрастанию, как хуки команд. Ядро берёт первого, чьи заявленные возможности подходят запросу |
| Описание | JSON из §4: что делает услуга и схема её параметров |

**Зарезервированные имена.** Плагин не может зарегистрировать имя, которое начинается с `host.` или `service.`, совпадает с `host`, `service` или с именем схемы ядра: `file`, `recycle`, `sys`, `find`, `ws`. Регистрация отклоняется с кодом ошибки `-32003`.

**Ленивая загрузка.** Плагин с услугами перечисляет их имена в массиве `services` файла `plugin.json`; ядро загружает такой плагин, когда приходит запрос на одно из имён (так же, как плагин загружается по своей схеме). Плагин без массива регистрирует услуги только после загрузки по другой причине.

**Отключение поставщика.** У плагинов, которые предлагают услуги (Everything, ripgrep, просмотр документов), в диалоге настроек есть опция «Предлагать плагин как поставщика услуг JSON-RPC». Когда пользователь её снимает (настройка плагина `jsonrpc_provider` = `0`), при следующей загрузке плагин не регистрирует услуги, и ядро его не вызывает. Опцию применяет `TServiceProvider.Register` в `uPluginServiceProvider.pas`, диалог находится в `uPluginServiceSettings.pas`; плагин другого рода добавляет такой же диалог через `RegisterServiceSettings`.

## 3. Сообщения

Каждое сообщение – один JSON-объект в UTF-8 по [JSON-RPC 2.0](https://www.jsonrpc.org/specification). Пакеты (массив запросов) не используются.

- **Запрос:** `{"jsonrpc":"2.0","id":1,"method":"search.files","params":{...}}`. `id` – целое или строка, уникальная среди открытых запросов вызывающего.
- **Ответ:** `{"jsonrpc":"2.0","id":1,"result":{...}}` или `{"jsonrpc":"2.0","id":1,"error":{"code":-32602,"message":"..."}}`.
- **Уведомление:** сообщение без `id`; ответа на него нет.

`method` запроса – имя услуги либо `service.describe` / `service.ping` (§4).

### 3.1. Коды ошибок

| Код | Смысл |
|---|---|
| `-32700` | Сообщение не является корректным JSON |
| `-32600` | Сообщение не является корректным объектом JSON-RPC |
| `-32601` | Нет поставщика для метода |
| `-32602` | Параметры не соответствуют схеме услуги |
| `-32603` | Внутренняя ошибка поставщика или ядра |
| `-32001` | Вызов отменён |
| `-32002` | Поставщик не может выполнить этот запрос (нет программы, неподдерживаемое условие); вызывающий переходит на свой способ |
| `-32003` | Не разрешено: зарезервированное имя, отказ в праве |
| `-32004` | Слишком много открытых вызовов услуги |
| `-32005` | Поставщик не ответил за отведённое время |

`message` – короткий текст для журнала; пользователю он как есть не показывается. Подробности – в `error.data` (объект).

## 4. Общие методы

### 4.1. `service.describe`

Запрос без параметров. Результат описывает, что предлагает поставщик:

```json
{
  "protocolVersion": 1,
  "name": "search.files",
  "version": 1,
  "title": "Everything",
  "description": "Finds files by name with the Everything index",
  "inputSchema": {
    "type": "object",
    "properties": {
      "root":   {"type": "string"},
      "mask":   {"type": "string"},
      "subdirs": {"type": "boolean"},
      "caseSensitive": {"type": "boolean"}
    },
    "required": ["root", "mask"]
  },
  "capabilities": ["name", "mask", "path", "size", "date"]
}
```

- `inputSchema` – объект JSON Schema с типами `object`, `string`, `integer`, `number`, `boolean`, `array` и ключевыми словами `properties`, `required`, `enum`, `items`. Ядро проверяет параметры запроса по ней до вызова и само отвечает `-32602`.
- `name`, `description` и `inputSchema` имеют ту же форму, что запись обычного «списка инструментов» серверов JSON-RPC, поэтому внешний процесс отображается на услугу без изменения данных (см. §10).
- `capabilities` – список строк, с которыми ядро сопоставляет потребности запроса. Слова каждой услуги определены в разделе этой услуги (§8).

### 4.2. `service.ping`

Запрос без параметров; результат `{}`. Ядро использует его для поставщика в другом процессе; поставщик в библиотеке отвечает сразу.

---

## 5. Результаты, прогресс и отмена

**Результат вызова.** Поставщик возвращает объект:

```json
{
  "content": [{"type": "text", "text": "12 files found"}],
  "structuredContent": {"hits": 12, "truncated": false},
  "isError": false
}
```

- `content` – текст для человека (список объектов с `type` равным `text`).
- `structuredContent` – данные для программы; форму определяет услуга (§8).
- `isError` равен `true`, когда услуга отработала и сообщает о сбое своей задачи (например, нечитаемая папка); сбои уровня протокола идут через объект `error` из §3.1.

**Прогресс.** Пока вызов идёт, поставщик может присылать уведомления:

```json
{"jsonrpc":"2.0","method":"notifications/progress","params":{"progressToken":"1","progress":120,"total":0,"message":"C:\\Work"}}
```

`progressToken` – `id` запроса; `total` равен 0, если неизвестен. Ядро показывает `message` в строке задания. Частичные данные услуги идут в уведомлениях самой услуги (для `search.files` – `search.hits`, §8).

**Отмена.** Вызывающий отменяет вызов через `CancelService` (§6); ядро сразу отвечает вызывающему ошибкой `-32001` и посылает поставщику уведомление `{"jsonrpc":"2.0","method":"notifications/cancelled","params":{"requestId":1,"reason":"cancelled"}}`. Поставщик обязан прекратить работу и освободить занятое вызовом; всё, что он пришлёт по этому вызову позже, ядро отбрасывает. Вызов, который закончился по другой причине (лимит времени, выгрузка поставщика), закрывается так же.

## 6. Host API (ABI 11)

Функции добавляются в конец таблицы Host API, поэтому плагин, собранный под более старый ABI, продолжает работать. Плагин, которому они нужны, сначала проверяет `AHostApi^.AbiVersion >= 11`. Все тексты – UTF-8; «основной поток» – поток, в котором работают остальные обратные вызовы плагина.

| Функция | Назначение |
|---|---|
| `RegisterService(pluginId, name, version, describeJson, handler, userData, priority)` | Предлагает услугу (основной поток). 0 – зарегистрирована, иначе код ошибки: `-32003` для зарезервированного имени, `-32602` для неверного аргумента. Повторная регистрация имени тем же плагином заменяет прежнюю |
| `ServiceReply(call, responseJson)` | Завершает вызов поставщика; из любого потока, один раз на вызов. 0 – поставлено в очередь, -1 – недопустимо |
| `ServiceNotify(call, notificationJson)` | Отправляет вызывающему прогресс или частичные данные идущего вызова; из любого потока. 0 – поставлено в очередь, -1 – недопустимо |
| `CallService(pluginId, name, requestJson, timeoutMs, buf, bufSize, negotiatedSize)` | Синхронный вызов (основной поток). `pluginId` пустой или `NULL` – первый поставщик. `timeoutMs` – 1..60000. 0 – ответ в `buf`; -2 – `buf` мал, `negotiatedSize` – нужный размер; иначе код ошибки |
| `CallServiceAsync(pluginId, name, requestJson, timeoutMs, onMessage, userData, jobId)` | Асинхронный вызов (основной поток): возвращается сразу; `onMessage` получает уведомления, затем ответ. 0 – запущен, иначе код ошибки и сообщений не будет |
| `ServiceStatus(jobId, buf, bufSize)` | Состояние вызова в JSON: `state` (`running`, `done`, `cancelled`, `failed`), `progress`, `total`, `message`. Текстовый результат как у остальных текстовых функций; -1 – такого вызова нет |
| `CancelService(jobId)` | Запрашивает отмену (§5) (основной поток). 0 – отменён, -1 – вызов не открыт |

У выгружаемого плагина пропадают услуги, а открытые на них вызовы завершаются ошибкой `-32603`. Поле манифеста `"services": ["search.files"]` перечисляет имена, которые регистрирует плагин; ядро загружает плагин при первом обращении к одному из них.

Обработчик поставщика: `function(userData: Pointer; call: Int64; requestJson: PAnsiChar): Int64; cdecl;`. Он должен возвращаться быстро: для запроса (`call` не равен 0) запускает работу, возможно в своём потоке, и завершает её через `ServiceReply`; для уведомления (`call` равен 0) только читает его. Возвращает 0, если сообщение принято.

Обратный вызов вызывающего: `procedure(userData: Pointer; jobId: Int64; messageJson: PAnsiChar); cdecl;`. Текст действителен только во время вызова.

## 7. Потоки, лимиты, безопасность

- **Потоки.** Поставщик отвечает из любого потока. Ядро переносит каждое сообщение для вызывающего в основной поток до запуска `onMessage`, в порядке отправки поставщиком; ответ всегда последнее сообщение вызова. `CallService` ждёт в основном потоке и пока ждёт доставляет остальные сообщения, поэтому годится только для быстрых услуг; для заданий, видимых пользователю, ядро использует `CallServiceAsync`.
- **Лимиты.** Одно сообщение – не больше 4 МиБ. Одновременно идёт не больше 8 вызовов одной услуги; следующий получает `-32004`. У вызова есть лимит времени, который задаёт вызывающий, не больше 60 с; он считается от последнего сообщения поставщика (уведомление начинает отсчёт заново); без лимита вызов может молчать сколько нужно. Поставщику, молчавшему весь лимит, отвечают `-32005`, и его вызов отменяется.
- **Безопасность.** Поставщик доверен настолько же, насколько его плагин (§1 [PLUGIN_BOUNDARIES.ru.md](PLUGIN_BOUNDARIES.ru.md)). Поставщик, который запускает другую программу, собирает список аргументов без оболочки и никогда не берёт путь к программе из данных запроса. Параметры запроса никогда не вставляются в командную строку одной строкой.
- **Исключения.** Исключение внутри обработчика получает ответ `-32603`; вызывающему оно не доходит сбоем.

## 8. Услуга `search.files`

Ищет файлы и папки. Alt+F7 сначала спрашивает зарегистрированных поставщиков и только потом обходит диск.

### 8.1. Параметры запроса

| Поле | Тип | Смысл |
|---|---|---|
| `root` | строка | Папка, где искать, локальный путь |
| `mask` | строка | Одна или несколько масок через `;`; пустая означает любое имя |
| `text` | строка | Текст, который должен содержать файл; пустая означает поиск только по именам |
| `regex` | булево | `text` – регулярное выражение |
| `caseSensitive` | булево | Учитывать регистр |
| `wholeWords` | булево | Только слова целиком |
| `subdirs` | булево | Искать в подпапках `root` |
| `includeFolders` | булево | В результат могут входить папки |
| `hidden` | булево | В результат могут входить скрытые и игнорируемые файлы |
| `encoding` | строка | Заданная кодировка текста файла; пустая означает определять |
| `minSize`, `maxSize` | целое | Байты; отсутствие поля означает без границы |
| `modifiedFrom`, `modifiedTo` | строка | Дата и время ISO 8601; отсутствие поля означает без границы |
| `maxResults` | целое | Сколько попаданий нужно вызывающему самое большее |

### 8.2. Возможности

Поставщик перечисляет слова того, что он выполняет: `name`, `mask`, `path`, `subdirs`, `case`, `words`, `size`, `date`, `folders`, `content`, `regex`, `encoding`, `hidden`. Ядро использует поставщика только если каждое слово, нужное запросу, есть в списке; запросу всегда нужны `name` и `mask`, а `content` – когда `text` не пуст. Границу, которую поставщик не выполняет (например, нижнюю границу размера), ядро применяет к попаданиям само.

### 8.3. Попадания и результат

Пока идёт поиск, поставщик присылает уведомление

```json
{"jsonrpc":"2.0","method":"search.hits","params":{"progressToken":"1","hits":[{"path":"C:\\Work\\a.txt","isDir":false,"size":120,"modified":"2026-01-02T03:04:05"}]}}
```

В массиве `hits` не больше 500 записей на сообщение; `size`, `modified`, `created`, `accessed` (локальное время ISO 8601) и `attributes` (биты атрибутов Windows) необязательны; чего в записи нет, то в списке результатов остаётся пустым. Итоговый ответ несёт сводку:

```json
{"jsonrpc":"2.0","id":1,"result":{"content":[{"type":"text","text":"12 found"}],"structuredContent":{"count":12,"truncated":false}}}
```

`truncated` равен `true`, когда поставщик остановился на `maxResults` или на своём пределе.

### 8.4. Выбор поставщика и запасной путь

Ядро берёт первого по приоритету поставщика, чьи возможности подходят запросу. Запрос с условием, которого не выполняет ни один поставщик (шаблон байтов, файлы внутри архивов, атрибуты, нелокальный корень), обслуживает встроенный обход. Если выбранный поставщик отвечает `-32002`, `-32005` или другой ошибкой до первого попадания, ядро запускает встроенный обход и показывает короткую пометку в строке состояния. После первого попадания ошибка завершает поиск с уже найденным.

## 9. Услуга `text.extract`

Превращает документ в обычный текст. Поиск по содержимому в Alt+F7 обращается к ней для файлов, расширение которых обслуживает поставщик, поэтому `.docx` или `.pdf` ищутся по тексту, а не по байтам.

### 9.1. Параметры запроса

| Поле | Тип | Смысл |
|---|---|---|
| `path` | строка | Локальный путь документа |
| `maxChars` | целое | Наибольшее число символов текста, которое нужно вызывающему |

### 9.2. Возможности

Поставщик перечисляет слово `ext.<расширение>` для каждого читаемого расширения (в нижнем регистре, без точки): `ext.docx`, `ext.pdf`. Ядро обращается к поставщику только для расширения из его списка. Если расширение не указал ни один поставщик, файл читается как есть.

### 9.3. Результат

```json
{"jsonrpc":"2.0","id":1,"result":{"content":[{"type":"text","text":"1200 characters"}],"structuredContent":{"text":"...","truncated":false}}}
```

`truncated` равно `true`, когда текст обрезан по `maxChars`. Файл, который поставщик прочитать не может, получает ответ `-32002`, неверные параметры – `-32602`; ядро тогда считает, что файл искомого текста не содержит. Файл без текста даёт пустой `text`.

### 9.4. Использование поиском

Встроенный обход читает такой файл через услугу и ищет текст в ответе. Когда поиск обслуживает поставщик `search.files` (например, ripgrep), ядро после его завершения делает второй проход по файлам обслуживаемых расширений и показывает файл, найденный обоими, один раз. Флажок «Использовать плагины» в диалоге поиска отключает и то и другое.

## 10. Совместимость с внешними процессами

Формат сообщений (JSON-RPC 2.0), форма описания (`name`, `description`, `inputSchema`), результат вызова (`content`, `structuredContent`, `isError`), а также имена и поля уведомлений о прогрессе и отмене следуют соглашениям распространённых серверов инструментов на JSON-RPC. Поэтому плагин, который запускает внешний процесс, проводит согласование версии, читает его список инструментов и регистрирует каждый инструмент как услугу, может передавать сообщения почти без изменений. Такой плагин-мост запланирован; он не входит в контракт выше и вводит свои правила запуска программ (явная настройка пользователя для каждой программы, путь к программе не берётся из данных, ограничения на размер сообщения и время).

Различия, которые мост обязан учесть:

- Внешний сервер возвращает список результатов целиком или страницами; мост превращает страницы в сообщения `search.hits`.
- `service.describe` услуги, которую регистрирует мост, строится из описания инструмента сервера; `capabilities` берутся из настроек моста.
